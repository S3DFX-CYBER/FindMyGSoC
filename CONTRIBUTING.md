# Contributing to FindMyGSoC

Thanks for taking the time to contribute. This guide is the same for everyone:
whether you arrived from NSoC, GSSoC, Hacktoberfest, or just found the repo, the
path from "I want to help" to "merged" is identical. There are no separate
tracks and no separate rules.

## Ways to contribute

Code is the smallest part of what this project needs.

| Contribution | Where to start |
|---|---|
| Report a bug | Open an issue with the bug template: what you did, what happened, what you expected, and your browser. |
| Suggest a feature | Open an issue with the feature template. Describe the problem before the solution. |
| Fix or build something | Pick up an issue labelled `good first issue` or `help wanted`. Comment on it first so nobody duplicates work. |
| Improve the data | Organisation details, mentor contacts and issue datasets live in `data/` and are generated by `scripts/`. Fixes there are very welcome. |
| Write or fix docs | README, `docs/`, and the in-app guide all take corrections. |
| Design or accessibility | Contrast, focus states, keyboard paths and screen reader behaviour are always open for improvement. |

## Set up locally

No build step, no framework, no package to install to run the site.

```bash
git clone https://github.com/S3DFX-CYBER/FindMyGSoC.git
cd FindMyGSoC
npx serve . -l 3000        # then open http://localhost:3000
```

For the tooling (lint, tests, data validation):

```bash
npm ci
npm test                   # 38 tests, node:test, no framework
npm run lint               # ESLint, Stylelint, HTMLHint
npm run validate:data      # checks the generated datasets
```

Requirements: Node 20 or newer. Nothing else.

## Find something to work on

1. Browse the open issues. `good first issue` means what it says.
2. Comment on the issue and wait to be assigned. This avoids two people writing
   the same patch.
3. If you want to work on something that is not filed yet, open an issue first
   and describe it. Small fixes can skip that step.

## Make the change

Branch from `main`:

```bash
git checkout -b fix/org-card-overflow
```

Use a prefix that matches the work: `feat/`, `fix/`, `docs/`, `chore/`, `refactor/`.

While you work:

- Keep the diff focused. One issue, one pull request. Unrelated cleanups belong
  in their own PR.
- Match the surrounding code. It is plain HTML, CSS and JavaScript on purpose.
- Run `npm run lint` and `npm test` before you push. CI runs both.

## Commit and sign off

This repository uses the [Developer Certificate of Origin](https://developercertificate.org/).
Every commit must be signed off, which is one flag:

```bash
git commit -s -m "fix: stop the org card title overflowing"
```

That appends:

```
Signed-off-by: Your Name <you@example.com>
```

If you forget, `git commit --amend -s --no-edit` fixes the last commit, and
`git rebase --signoff main` fixes a whole branch.

Write commit messages in the [Conventional Commits](https://www.conventionalcommits.org/)
style: `feat:`, `fix:`, `docs:`, `chore:`, `refactor:`, `test:`. A subject line
in plain English beats a clever one.

## Open the pull request

Fill in the template. Two fields matter more than the rest:

- **Related issue.** `Closes #123` in the body. A PR without a linked issue is
  closed rather than reviewed.
- **What changed and why.** Two or three sentences. Reviewers should not have to
  read the diff to understand the intent.

Attach a screenshot or a short recording for anything visual. Before and after
is even better.

## What gets reviewed

Several things run automatically when you open a PR:

| Check | What it does |
|---|---|
| DCO | Confirms every commit is signed off. |
| Code Quality | Runs `npm run lint` and `npm test`. |
| Review bots | Read the diff and leave comments. They are useful but not always right. |
| Maintainer review | The decision that matters. |

Reviewers will look for:

- Does it fix the reported problem, and only that problem?
- Does it follow the house rules below?
- Is anything user-facing escaped, validated and reachable by keyboard?
- Do lint and tests still pass?

Push follow-up commits to the same branch rather than opening a second PR. If a
review comment is wrong, say so in the thread with your reasoning and resolve it.

## House rules

These are not style preferences. A PR that breaks one of them will be sent back.

1. **No build step.** The site must keep working by opening `index.html`. No
   bundler, no framework, no transpiler.
2. **No new runtime dependencies.** The browser side runs on vanilla JavaScript.
   Dev dependencies for linting and testing are fine.
3. **Static first.** Anything that can be computed from `data/` in the browser
   should be. Reach for an edge function only when the data has to be live.
4. **Two copies of the app script.** `index.html` carries an inline script and
   `src/js/app.js` mirrors it. Logic changes go in both, or the behaviour drifts.
5. **Escape untrusted data.** Organisation names, issue titles, resume text and
   search input all come from outside. Use the escaping helpers, never raw
   `innerHTML` with interpolated data.
6. **Validate outbound links.** Anything from an API or a dataset goes through
   the URL validator before it becomes an `href`.
7. **Keep it accessible.** New controls need a label, a focus state, and a
   keyboard path. Modals trap focus and return it on close.
8. **Respect the data.** Do not hand-edit generated datasets. Change the script
   in `scripts/` and regenerate.

## Using AI tools

AI assistance is welcome. Unreviewed AI output is not. You are responsible for
every line you submit, and reviewers will ask you to explain it.

- Read [AI_POLICY.md](AI_POLICY.md) for what is and is not acceptable.
- If you are an agent working in this repository, read [AGENTS.md](AGENTS.md)
  first: it covers the constraints, the file map and the checks to run.
- Disclose substantial AI assistance in the PR description. It does not count
  against you; pretending otherwise does.

## Questions

Open a discussion or ask in the issue thread. There is no such thing as a
question that is too basic, and a question asked before you write the patch
saves everyone a review cycle.
